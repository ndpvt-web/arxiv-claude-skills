# VISOR: Visual Spatial Object Reasoning for Language-Driven Navigation

This skill teaches Claude to implement VISOR's three-stage reasoning architecture — **think**, **think-summary**, **action** — for building embodied agents that navigate to objects described in natural language. Instead of opaque end-to-end models or brittle multi-model pipelines, this approach uses a single compact Vision-Language-Action (VLA) model that explicitly reasons about what it sees, why it should act, and which action to take. The technique is applicable to any task requiring grounded visual-spatial decision-making: robotic navigation, visual question answering with spatial context, or autonomous agents operating in simulated/real environments.

## When to Use

- When the user wants to build an embodied navigation agent that interprets natural language target descriptions (e.g., "find the red mug on the shelf near the window")
- When implementing a Vision-Language-Action (VLA) model that needs explainable decision-making, not just action prediction
- When designing a chain-of-thought reasoning pipeline for visual grounding — matching language descriptions to objects in images
- When replacing a brittle multi-model pipeline (separate detector + LLM planner + navigator) with a unified reasoning agent
- When fine-tuning a small vision-language model (e.g., Qwen2.5-VL 3B) for action selection in navigation or manipulation tasks
- When building a spatial reasoning system that must distinguish objects by both intrinsic attributes (color, shape, material) and extrinsic attributes (relative position, room context, spatial relations)

## Key Technique

VISOR's core insight is that embodied navigation should be treated as **explicit visual reasoning** rather than embedding similarity or pipeline orchestration. Traditional approaches either (a) train end-to-end models that map vision-language embeddings directly to actions — which fail to generalize and offer no explainability — or (b) chain together separate models (object detector, LLM reasoner, path planner) that suffer from cascading errors and high latency. VISOR replaces both with a single 3B-parameter VLA model that generates structured reasoning before selecting actions.

The reasoning unfolds in three stages using XML-style tags. In the **`<think>`** stage, the model produces detailed, image-grounded reasoning: it examines the panoramic observation and top-down map, identifies candidate waypoints, evaluates whether visible objects match the target description, and considers spatial layout. In the **`<think_summary>`** stage, it distills this analysis into a concise rationale capturing the key factors driving the decision. In the **`<action>`** stage, it outputs the selected waypoint label or STOP command. This decomposition forces the model to "show its work" and grounds every action in visual evidence.

Training follows a two-phase approach: first, supervised fine-tuning (SFT) on reasoning traces generated by GPT-4o teaches the model the structured reasoning format; then, Group Sequence Policy Optimization (GSPO) — a reinforcement learning method — refines the policy using only action-level rewards, allowing the model to develop its own reasoning strategies without needing explicit trace supervision. Critically, ground-truth object locations are hidden from the reasoning traces during SFT, forcing the model to learn genuine perceptual grounding rather than shortcut memorization.

## Step-by-Step Workflow

1. **Define the observation space.** Construct the visual input as a panoramic RGB image (concatenated from multiple camera views, e.g., 768x256 from three 90-degree FOV cameras) and a top-down occupancy/semantic map (e.g., 256x256) built online from depth projection. Both images serve as input to the VLA model alongside the natural language instruction.

2. **Generate navigable waypoint candidates.** From depth data, project valid floor points into 3D space, cluster them using DBSCAN, and overlay labeled waypoint markers (e.g., "A", "B", "C") directly onto the panoramic image. Randomize label assignment across episodes to prevent the model from memorizing position-label mappings.

3. **Structure the prompt with three-stage reasoning format.** Build the system prompt to instruct the model to reason in `<think>`, `<think_summary>`, and `<action>` blocks. The system prompt should specify: "Examine the panoramic view and map. Identify which waypoint leads toward the target object described in the instruction. Reason step by step, grounding your analysis in visual evidence."

4. **Prepare SFT training data with reasoning traces.** For each training sample, provide: the target description, panoramic image, top-down map, waypoint labels, and a structured reasoning trace. Generate traces using a teacher model (e.g., GPT-4o) that has access to ground-truth object locations, but **exclude ground-truth from the trace text itself** — the trace must reason from visual evidence only.

5. **Fine-tune the base VLA model with SFT.** Use cross-entropy loss on the structured output tokens (think + think_summary + action). Freeze the visual backbone if compute is limited. Use a learning rate around 5e-5 with standard AdamW. This phase teaches the reasoning format and basic visual grounding.

6. **Apply RL post-training with GSPO.** After SFT, run Group Sequence Policy Optimization: sample multiple action sequences per state, reward correct waypoint selection (and correct STOP decisions near the goal), and update the policy with a KL penalty (beta ~0.01) against the SFT checkpoint. This phase improves action accuracy without requiring explicit reasoning supervision.

7. **Implement the inference loop.** At each navigation step: capture the panoramic image and update the top-down map, overlay current waypoint candidates, feed the combined observation + instruction to the VLA, parse the `<think>`, `<think_summary>`, and `<action>` tags from the output, and execute the selected waypoint via a shortest-path planner (e.g., A* on the occupancy grid).

8. **Add the STOP decision mechanism.** Train the model to output STOP when it believes it has reached the target object. Include distance-to-goal as an implicit signal during training. At inference, execute STOP when the model predicts it, and evaluate success based on proximity to the ground-truth target (typically within 1m).

9. **Parse and log the reasoning chain for explainability.** Extract the `<think>` and `<think_summary>` blocks at each step to create an audit trail of the agent's decision process. This is essential for debugging navigation failures and understanding where visual grounding breaks down.

10. **Evaluate on standard benchmarks.** Test on REVERIE/SOON-style language navigation benchmarks or custom scenarios. Track Success Rate (SR), Success weighted by Path Length (SPL), and per-category generalization to unseen object types and environments.

## Concrete Examples

**Example 1: Building a VISOR-style navigation agent with Qwen2.5-VL**

User: "I want to build an object navigation agent that can find objects from language descriptions in a simulated home environment. It should explain its reasoning."

Approach:
1. Set up Habitat or AI2-THOR simulator with RGB-D observations
2. Use Qwen2.5-VL-3B as the base VLA model
3. Implement the three-stage prompt structure
4. Fine-tune on navigation episodes with reasoning traces

Output — System prompt and inference code structure:
```python
SYSTEM_PROMPT = """You are a visual navigation agent. Given:
- A panoramic RGB image with labeled waypoint candidates
- A top-down map of explored areas
- A target object description

Reason about which waypoint to navigate to (or whether to STOP).
Structure your response as:
<think>Detailed reasoning examining the panoramic view, identifying
visible objects, assessing spatial layout, and evaluating each
waypoint candidate against the target description.</think>
<think_summary>One-sentence rationale for the chosen action.</think_summary>
<action>LABEL or STOP</action>"""

def navigation_step(model, panoramic_img, topdown_map, instruction, waypoints):
    # Overlay waypoint labels on panoramic image
    labeled_pano = overlay_waypoints(panoramic_img, waypoints)

    messages = [
        {"role": "system", "content": SYSTEM_PROMPT},
        {"role": "user", "content": [
            {"type": "image", "image": labeled_pano},
            {"type": "image", "image": topdown_map},
            {"type": "text", "text": f"Find: {instruction}\nWaypoints: {list(waypoints.keys())}"}
        ]}
    ]

    output = model.generate(messages, max_tokens=512)
    think, summary, action = parse_visor_output(output)
    return action, {"reasoning": think, "summary": summary}

def parse_visor_output(text):
    think = extract_between(text, "<think>", "</think>")
    summary = extract_between(text, "<think_summary>", "</think_summary>")
    action = extract_between(text, "<action>", "</action>").strip()
    return think, summary, action
```

**Example 2: Generating SFT training data with reasoning traces**

User: "How do I create the training dataset for the three-stage reasoning format?"

Approach:
1. Collect navigation episodes with ground-truth paths
2. At each step, record panoramic image, map, waypoints, and correct action
3. Use GPT-4o to generate reasoning traces (without leaking ground-truth location)
4. Format as structured training samples

Output — Data generation pipeline:
```python
TRACE_GENERATION_PROMPT = """You are generating training data for a navigation agent.
Given the panoramic image with waypoint labels and a target description,
write a reasoning trace explaining which waypoint to choose.

CRITICAL: Do NOT reference ground-truth coordinates or distances.
Only reason from what is VISIBLE in the image and map.

Target: {instruction}
Correct waypoint: {gt_label}

Generate:
<think>[Detailed visual reasoning: What objects are visible? What does
the spatial layout suggest? Why does waypoint {gt_label} lead toward
the target?]</think>
<think_summary>[One sentence distilling the key reasoning.]</think_summary>
<action>{gt_label}</action>"""

def generate_training_sample(episode_step, teacher_model):
    trace = teacher_model.generate(
        TRACE_GENERATION_PROMPT.format(
            instruction=episode_step["instruction"],
            gt_label=episode_step["ground_truth_waypoint"]
        ),
        images=[episode_step["panoramic"], episode_step["topdown_map"]]
    )
    return {
        "images": [episode_step["panoramic"], episode_step["topdown_map"]],
        "instruction": episode_step["instruction"],
        "waypoint_labels": episode_step["waypoint_candidates"],
        "target_output": trace  # Full <think>...<action> structure
    }
```

## Best Practices

- **Do:** Randomize waypoint/object label assignments across episodes to prevent position-label memorization. VISOR uses random letter assignment specifically to force visual grounding.
- **Do:** Keep the `<think>` stage verbose and the `<think_summary>` stage to one sentence. This mirrors VISOR's design where detailed reasoning is distilled into a compact rationale before action selection.
- **Do:** Exclude ground-truth spatial information from reasoning traces during SFT data generation. If the teacher model references privileged information (exact distances, coordinates), the student learns shortcuts instead of perceptual grounding.
- **Do:** Use RL post-training (GSPO or PPO) after SFT to let the model develop its own reasoning strategies beyond the teacher's traces.
- **Avoid:** Feeding raw embedding similarities as input. VISOR's advantage comes from explicit, interpretable reasoning — replacing this with cosine similarity scores undermines the approach.
- **Avoid:** Using history-dependent architectures. VISOR operates under a Markovian assumption (current observation only). While this simplifies training, add explicit state tracking (e.g., visited locations on the map) if your task requires memory.

## Error Handling

- **Label hallucination:** The model may output a waypoint label that doesn't exist in the current candidate set. Always validate the `<action>` output against the current valid labels. Fall back to the closest valid label or re-prompt.
- **Reasoning-action mismatch:** The `<think>` block may reason toward one waypoint but the `<action>` selects another. Log these discrepancies — they indicate the RL phase has diverged from the SFT reasoning. Consider increasing the KL penalty (beta) during RL training.
- **Parse failures:** If the model doesn't produce well-formed XML tags, implement a fallback parser that extracts the last word/token as the action. During training, enforce the tag structure through formatting constraints in the loss function.
- **STOP oscillation:** The agent may alternate between STOP and movement near the target. Implement a confidence threshold: if STOP is predicted N times in M steps, force termination.
- **Spatial confusion with symmetric layouts:** The model may struggle in environments with repeated structures (e.g., identical doors in a hallway). Augment the top-down map with visited-area markers to provide disambiguation context.

## Limitations

- **Markovian assumption:** VISOR conditions only on the current observation, not history. This means overshooting a target or entering a dead-end requires the agent to re-derive context from scratch, limiting recovery in complex layouts.
- **3B parameter scale:** While compact, this model size may not capture fine-grained visual distinctions for very similar objects (e.g., distinguishing two nearly identical mugs by subtle texture differences). Scaling to 7B+ may be needed for precision tasks.
- **Simulation-to-real gap:** VISOR is trained and evaluated in simulation (Habitat). Deploying to real robots requires domain adaptation for noisy depth, varying lighting, and imperfect odometry.
- **No multi-turn dialogue:** The agent processes a single instruction. It cannot ask clarifying questions ("Which blue box — the large or small one?"). For ambiguous descriptions, consider adding a clarification stage before the think chain.
- **Reasoning traces require a teacher model:** SFT data generation depends on a capable teacher (GPT-4o) to produce grounded reasoning traces. Without high-quality traces, the three-stage format degrades to a formatting gimmick rather than genuine reasoning.
