# AI-Generated Code Detection with AICD Bench

This skill enables Claude to build, evaluate, and apply AI-generated code detection systems using the methodology from AICD Bench -- the most comprehensive benchmark for distinguishing human-written code from machine-generated code. It covers three detection tasks: binary human/machine classification robust to distribution shifts, model family attribution (identifying which LLM family produced the code), and fine-grained classification across human, machine, hybrid, and adversarial categories. The approach combines classical feature engineering (TF-IDF, AST analysis, stylometric signals) with neural detectors (CodeBERT, ModernBERT) and critically accounts for the failure modes that make naive detectors useless in practice.

## When to Use

- When a user asks to determine if a code snippet was written by a human or generated by an AI
- When building a classifier to detect AI-generated code across multiple programming languages
- When a user needs to attribute code to a specific LLM family (DeepSeek, Qwen, Llama, GPT, Gemini, etc.)
- When evaluating whether an existing AI-code detector generalizes to unseen languages or model families
- When a user wants to detect hybrid code (human skeleton + AI completion) or adversarial code (AI code designed to look human)
- When assessing code provenance for security audits, academic integrity, or supply chain trust
- When building a training pipeline for code detection and needing a rigorous benchmark dataset

## Key Technique

AICD Bench identifies that most AI-code detectors fail catastrophically under **distribution shift** -- a detector trained on Python code from GPT-4 will not reliably detect Rust code from DeepSeek. The benchmark defines four progressively harder test conditions: (1) seen language + seen domain, (2) unseen language + seen domain, (3) seen language + unseen domain, (4) unseen language + unseen domain. The best classical detector (SVM with TF-IDF trigrams) achieves only 0.43 macro F1 on the hardest binary task, and the best neural detector (ModernBERT) reaches just 0.33 F1 on family attribution. This means any production detector **must** be designed with cross-distribution robustness as a first-class concern.

The feature extraction pipeline combines three complementary signal sources. **Token-level features** use TF-IDF over uni/bi/trigrams (whitespace-delimited, no lowercasing) reduced to 500 dimensions via SVD, capturing statistical token distribution differences. **Structural features** use Tree-Sitter AST parsing to extract 543-1,030 features per language: AST depth, node type counts (if-statements, loops, function definitions), control-flow density, and construct distributions. **Stylometric features** capture layout indicators like empty-line density, max/average line length, docstring patterns, variable naming conventions, and alphanumeric character fractions. These three feature sets feed into classical classifiers (SVM, Random Forest, Logistic Regression) or are replaced by contextual embeddings from fine-tuned encoder models.

The critical insight is that **hybrid and adversarial code break all current detectors**. Hybrid code (human-authored code rewritten by LLaMA 3.3 70B) and adversarial code (generated with DPO alignment to mimic human style) cause in-domain F1 to drop from 0.366 to 0.119 out-of-domain. Any practical system must either explicitly model these categories or accept significant blind spots.

## Step-by-Step Workflow

1. **Identify the detection task scope.** Determine which of three tasks applies: binary detection (human vs. machine), family attribution (which LLM family), or fine-grained classification (human/machine/hybrid/adversarial). Each requires different label schemes and training strategies.

2. **Collect or load the benchmark data.** Load AICD Bench from HuggingFace for evaluation or training:
   ```python
   from datasets import load_dataset
   # T1 = binary classification, T2 = family attribution, T3 = fine-grained
   ds = load_dataset("AICD-bench/AICD-Bench", name="T1")
   train, val, test = ds["train"], ds["validation"], ds["test"]
   # Schema: {'code': str, 'label': int, 'split': str}
   ```
   T1 has 1.71M rows, T2 has 1.11M, T3 has 2.1M. For custom data, collect code samples with known provenance.

3. **Extract token-level features via TF-IDF.** Tokenize code by whitespace (preserve casing and special characters -- code tokens are case-sensitive). Build uni-, bi-, and trigram vocabularies. Apply TF-IDF weighting, then reduce to 500 dimensions with truncated SVD:
   ```python
   from sklearn.feature_extraction.text import TfidfVectorizer
   from sklearn.decomposition import TruncatedSVD

   tfidf = TfidfVectorizer(
       analyzer='word', token_pattern=r'\S+',
       ngram_range=(1, 3), max_features=50000,
       lowercase=False, sublinear_tf=True
   )
   X_tfidf = tfidf.fit_transform(code_samples)
   svd = TruncatedSVD(n_components=500, random_state=42)
   X_reduced = svd.fit_transform(X_tfidf)
   ```

4. **Extract structural features via AST parsing.** Use Tree-Sitter to parse each code sample and extract: AST depth, total node count, counts per node type (function_definition, if_statement, for_statement, etc.), number of unique identifiers, lines of code, and control-flow density (branches per LOC):
   ```python
   import tree_sitter_python as tspython
   from tree_sitter import Language, Parser

   PY_LANGUAGE = Language(tspython.language())
   parser = Parser(PY_LANGUAGE)
   tree = parser.parse(bytes(code, 'utf8'))

   def extract_ast_features(node, depth=0):
       features = {'max_depth': depth, 'node_count': 1}
       features[f'type_{node.type}'] = 1
       for child in node.children:
           child_feats = extract_ast_features(child, depth + 1)
           # merge counts...
       return features
   ```

5. **Extract stylometric features.** Compute: average and max line length, empty-line ratio, indentation consistency (tabs vs. spaces, indentation depth variance), variable naming convention ratios (snake_case vs. camelCase vs. single-letter), comment density, and docstring presence:
   ```python
   import re
   lines = code.split('\n')
   features = {
       'avg_line_length': sum(len(l) for l in lines) / max(len(lines), 1),
       'max_line_length': max((len(l) for l in lines), default=0),
       'empty_line_ratio': sum(1 for l in lines if not l.strip()) / max(len(lines), 1),
       'snake_case_ratio': len(re.findall(r'\b[a-z]+_[a-z]+\b', code)) / max(len(re.findall(r'\b\w+\b', code)), 1),
       'comment_density': sum(1 for l in lines if l.strip().startswith('#')) / max(len(lines), 1),
   }
   ```

6. **Concatenate all feature vectors and train a classifier.** For classical detection, concatenate TF-IDF (500d), AST features (~500-1000d), and stylometric features (~20d), then train an SVM with RBF kernel or a Random Forest. For neural detection, fine-tune CodeBERT or ModernBERT for 3 epochs, batch size 64, 512-token input window:
   ```python

   import numpy as np
   X = np.hstack([X_tfidf_reduced, X_ast, X_style])
   clf = SVC(kernel='rbf', C=10, gamma='scale', class_weight='balanced')
   clf.fit(X_train, y_train)
   ```

7. **Evaluate under distribution shift.** Never report only in-distribution accuracy. Split test data into four quadrants: (seen lang, seen domain), (unseen lang, seen domain), (seen lang, unseen domain), (unseen lang, unseen domain). Report macro F1 for each quadrant separately. A detector that scores 0.90 in-distribution but 0.45 out-of-distribution is not production-ready.

8. **Test against hybrid and adversarial samples.** If building for Task 3, include hybrid code (human skeleton + AI rewrite) and adversarial code (AI with human-mimicking alignment) in evaluation. Expect a significant F1 drop -- this is the hardest category and the most realistic threat model.

9. **Analyze per-language and per-family performance.** Break down results by each of the 9 languages (Python, Java, C++, C, Go, PHP, C#, JavaScript, Rust) and by each of the 11 model families (DeepSeek, Qwen, Yi, StarCoder, Gemma, Phi, Llama, Granite, Mistral, OpenAI, Gemini). Identify which languages and families your detector handles poorly.

10. **Report results with calibrated confidence.** Given that SOTA detectors achieve at most 0.43-0.62 macro F1 on AICD Bench, communicate detection results as probabilistic assessments, never as binary verdicts. Flag uncertain cases explicitly.

## Concrete Examples

**Example 1: Quick single-snippet analysis**

User: "Can you tell if this Python function was written by an AI?"

Approach:
1. Extract stylometric signals from the provided code: line length distribution, naming conventions, comment patterns, blank line spacing.
2. Check for known AI generation tells: unusually consistent indentation, over-documented simple operations, formulaic variable names (`result`, `output`, `temp`), lack of shorthand idioms, excessive docstrings on trivial functions.
3. Parse the AST and check structural markers: uniform function complexity, suspiciously balanced if/else branches, absence of dead code or TODO comments.
4. Provide a probabilistic assessment with reasoning.

Output:
```

Signals detected:
- Variable naming is highly consistent (all snake_case, no abbreviations) -- unusual for human code
- Every function has a docstring, including 3-line helpers -- humans rarely document trivially
- Line lengths cluster tightly around 79 chars (PEP 8 max) with no outliers
- No TODO/FIXME comments, no commented-out code, no debugging artifacts
- Control flow is uniformly structured: every if has a matching else

Caveats: A disciplined human developer following strict linting could produce
similar patterns. Confidence would increase with more code from the same author.
These heuristics achieve ~60% accuracy on out-of-distribution code per AICD Bench.
```

## Best Practices

- **Do:** Always evaluate under distribution shift. In-distribution accuracy is misleading -- real-world code comes from unseen models and languages.
- **Do:** Combine multiple feature types (TF-IDF + AST + stylometric). No single signal source is sufficient. Token features capture vocabulary; AST features capture structure; style features capture formatting habits.
- **Do:** Preserve code casing and whitespace during TF-IDF tokenization. Code identifiers are case-sensitive, and `myVar` vs. `my_var` is a strong signal.
- **Do:** Report all results as probabilistic assessments with explicit confidence intervals. Never claim binary certainty about code authorship.
- **Avoid:** Training only on Python and expecting the model to generalize to Rust or Go. Cross-language transfer is the weakest link in current detectors.
- **Avoid:** Ignoring hybrid and adversarial categories. Real-world AI-assisted coding produces hybrid code (human writes the design, AI fills in the body), which breaks binary detectors.
- **Avoid:** Using line-count thresholds or simple regex heuristics as primary signals. These are trivially gamed and do not generalize.

## Error Handling

- **Tree-Sitter parse failure:** Some code snippets are fragments or contain syntax errors. Fall back to token-level and stylometric features when AST parsing fails. Log the failure rate per language -- if it exceeds 10%, check the Tree-Sitter grammar version.
- **Short code samples (< 6 lines):** Feature extraction becomes unreliable below ~6 lines of code. Flag these as "insufficient signal" rather than forcing a prediction.
- **Unseen programming language:** If the input language is not among the 9 supported languages (Python, Java, C++, C, Go, PHP, C#, JavaScript, Rust), fall back to language-agnostic features (TF-IDF + stylometric only). Warn the user that accuracy will be degraded.
- **Class imbalance:** If training data has unequal human/machine ratios, use `class_weight='balanced'` in SVM or stratified sampling. Report both macro F1 and per-class F1.
- **OOM on large datasets:** The full AICD Bench has 2M+ examples. Use streaming mode (`load_dataset(..., streaming=True)`) or sample subsets for rapid prototyping before scaling up.

## Limitations

- **SOTA is far below practical usability.** The best detectors achieve 0.43 macro F1 on binary classification under distribution shift and 0.33 on family attribution. Do not deploy these systems as sole decision-makers for academic integrity or legal judgments.
- **Rapid model evolution.** New LLM families and reasoning models (DeepSeek-R1, Qwen3) continuously change the distribution of AI-generated code. Detectors must be retrained regularly.
- **Hybrid code is fundamentally ambiguous.** When a human writes the algorithm and an AI fills in boilerplate, the concept of "authorship" itself becomes unclear. Detection systems cannot resolve this philosophical ambiguity.
- **Adversarial evasion is easy.** DPO-aligned models that mimic human coding style, or simple post-processing (variable renaming, comment insertion), can drop detector accuracy to near-random.
- **Language coverage gaps.** Languages outside the 9 supported ones (e.g., Kotlin, Swift, Ruby, Haskell) have no benchmark data and detector performance is unknown.
- **Feature extraction is language-dependent.** AST-based features require per-language Tree-Sitter grammars and produce different feature dimensions per language (543 for some, 1,030 for others), complicating multi-language pipelines.
