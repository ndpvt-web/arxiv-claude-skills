# VESPO: Variational Sequence-Level Soft Policy Optimization

This skill enables Claude to implement, configure, and debug the VESPO algorithm for stable off-policy reinforcement learning in LLM training. VESPO replaces brittle token-level clipping (as in GRPO) with a principled, closed-form gamma-shaped reshaping kernel that operates on sequence-level importance weights. It maintains training stability under extreme policy staleness (up to 64x), fully asynchronous rollout-training splits, and train-inference engine mismatches -- situations where standard methods like GRPO and SAPO collapse.

## When to Use

- When a user is building or modifying an RL training loop for LLMs and needs stable importance weight handling
- When GRPO or PPO training is collapsing due to stale rollouts, high staleness ratios, or asynchronous execution
- When the user asks how to handle sequence-level importance sampling without length normalization bias
- When implementing a custom policy loss function for off-policy LLM fine-tuning (RLHF, RLAIF, math reasoning RL)
- When the user wants to replace token-level clipping with a smooth, differentiable alternative
- When diagnosing length explosion, reward hacking, or gradient norm spikes during RL training of language models
- When configuring asymmetric treatment of positive vs. negative advantage samples in policy gradients

## Key Technique

**The core problem:** Off-policy RL for LLMs uses rollouts generated by a stale behavior policy mu that diverges from the current policy pi. Importance sampling corrects for this shift by weighting each trajectory by W = pi(tau)/mu(tau), but raw IS weights have catastrophically high variance -- a single outlier weight can destabilize training. Existing fixes are ad hoc: GRPO clips at the token level (breaking cross-token dependencies), GSPO normalizes by sequence length (introducing length-dependent bias that causes verbose output collapse), and SAPO uses soft gating (but under-suppresses negative-advantage outliers).

**VESPO's solution:** Reformulate reshaping as a constrained variational optimization problem. Define a proposal distribution Q(tau) proportional to mu(tau) * phi(W(tau)), then minimize a mixed KL divergence `(1 - alpha) * D_KL(Q || mu) + alpha * D_KL(Q || pi)` subject to a variance constraint `E_Q[W] <= C`. Solving the Lagrangian yields a closed-form reshaping kernel:

```
phi(W) = W^c1 * exp(c2 * (1 - W))
```

where `phi(1) = 1` preserves on-policy gradients exactly. The power term `W^c1` governs behavior for under-represented samples (W < 1), while the exponential `exp(c2 * (1 - W))` provides smooth, unbounded suppression for over-represented samples (W >> 1) -- no hard clip boundary, no length normalization needed.

**Asymmetric advantage handling:** Positive and negative advantage trajectories have different gradient dynamics. VESPO uses separate kernel parameters: `(c1=2.0, c2=3.0)` for positive advantages (moderate suppression, preserve learning signal) and `(c1=3.0, c2=2.0)` for negative advantages (stronger power suppression to prevent destabilizing penalty updates). This asymmetry prevents the length explosion observed when negative samples receive unchecked gradient contributions.

## Step-by-Step Workflow

1. **Compute sequence-level log importance weights in log-space.** For each trajectory tau with tokens y_1...y_T, compute `log_W = sum_t [log pi_theta(y_t | x, y_<t) - log mu(y_t | x, y_<t)]`. Never exponentiate individual token ratios -- accumulate in log-space to avoid numerical overflow.

2. **Compute the reshaping weight in log-space.** Calculate `log_phi = c1 * log_W + c2 * (1 - exp(log_W))`. For numerical stability, use the identity `1 - W = 1 - exp(log_W)` and compute the final phi only when needed for the loss.

3. **Split trajectories by advantage sign.** Compute advantages `A(tau) = R(tau) - baseline` using group-level normalization (mean/std within each prompt group). Partition into positive-advantage and negative-advantage sets.

4. **Apply asymmetric kernel parameters.** Use `(c1=2.0, c2=3.0)` for trajectories where `A > 0` and `(c1=3.0, c2=2.0)` for trajectories where `A < 0`. This is the default configuration validated across multiple model scales.

5. **Compute the policy gradient loss.** The surrogate loss is `L = -phi(W).detach() * A * sum_t log pi_theta(y_t | x, y_<t)`. Detach phi from the computation graph -- it serves as a fixed scaling coefficient, not a differentiable path.

6. **Do NOT apply length normalization.** Unlike GSPO or normalized IS methods, do not divide log_W or phi by sequence length T. Length normalization introduces bias toward verbose outputs and causes training collapse (validated by ablation: VESPOlin collapses at step ~350).

7. **Monitor diagnostic metrics.** Track: (a) `W_seq` mean/std/max to detect staleness drift, (b) `phi(W)` statistics to verify suppression is active, (c) KL divergence between pi and mu, (d) gradient norms, (e) response length distribution. Spikes in W_max or gradient norms indicate the kernel is encountering extreme staleness.

8. **Configure staleness ratio appropriately.** Set the number of gradient steps between rollout refreshes (N). VESPO is validated stable for N in {4, 8, 16, 32, 64}. Higher N increases throughput but requires the reshaping kernel to work harder -- monitor phi statistics at higher ratios.

9. **Integrate with existing frameworks.** VESPO slots into any REINFORCE/PPO-style training loop by replacing the clipped surrogate objective. In veRL, register the loss function via `@register`. In TRL or custom loops, replace the policy loss computation with the VESPO kernel.

## Concrete Examples

**Example 1: Implementing the VESPO loss in PyTorch**

User: "I have a GRPO training loop that's collapsing at staleness ratio 16. Help me replace the clipped loss with VESPO."

Approach:
1. Identify the existing clipped surrogate loss computation
2. Replace with sequence-level importance weight computation and gamma kernel
3. Add asymmetric parameter handling

Output:
```python
import torch

def vespo_policy_loss(
    log_probs: torch.Tensor,       # [B, T] current policy log probs
    old_log_probs: torch.Tensor,    # [B, T] behavior policy log probs
    advantages: torch.Tensor,       # [B] per-sequence advantages
    response_mask: torch.Tensor,    # [B, T] valid token mask
    k_pos: float = 2.0,
    lambda_pos: float = 3.0,
    k_neg: float = 3.0,
    lambda_neg: float = 2.0,
) -> torch.Tensor:
    # Step 1: Sequence-level log importance weight (NO length normalization)
    token_log_ratio = log_probs - old_log_probs          # [B, T]
    token_log_ratio = token_log_ratio * response_mask
    log_w_seq = token_log_ratio.sum(dim=-1)               # [B]

    # Step 2: Asymmetric kernel parameters by advantage sign
    pos_mask = (advantages > 0).float()
    neg_mask = (advantages <= 0).float()
    k = pos_mask * k_pos + neg_mask * k_neg
    lam = pos_mask * lambda_pos + neg_mask * lambda_neg

    # Step 3: Compute reshaping weight phi(W) in log-space
    # phi(W) = W^k * exp(lam * (1 - W)), normalized so phi(1) = 1
    w_seq = log_w_seq.exp()
    log_phi = k * log_w_seq + lam * (1.0 - w_seq)        # [B]
    phi = log_phi.exp()

    # Step 4: Compute loss (detach phi -- it's a fixed coefficient)
    per_token_loss = log_probs * response_mask
    sequence_log_prob = per_token_loss.sum(dim=-1)         # [B]
    loss = -(phi.detach() * advantages * sequence_log_prob).mean()

    return loss
```

**Example 2: Diagnosing training collapse from length normalization**

User: "My RL training produces increasingly long responses and the reward plateaus after 300 steps. What's going wrong?"

Approach:
1. Check whether the importance weight or loss computation divides by sequence length
2. If length normalization is present, it biases toward verbose outputs -- longer sequences have smaller per-token IS ratios, making them less likely to be clipped, so the model learns to produce longer text
3. Remove length normalization and apply VESPO's unnormalized kernel

## Best Practices

**Do:** Compute importance weights entirely in log-space (`log_w = sum of log-ratios`), exponentiating only for the final phi computation. This prevents numerical overflow that occurs with long sequences.

**Do:** Use the default asymmetric parameters `(k_pos=2.0, lambda_pos=3.0)` and `(k_neg=3.0, lambda_neg=2.0)` as a starting point. These were validated across Llama-3.2-3B, Qwen3-8B, and Qwen3-30B-A3B architectures.

**Do:** Detach `phi(W)` from the computation graph. It acts as a fixed scaling coefficient for the REINFORCE gradient -- backpropagating through it would introduce biased second-order terms.

**Do:** Monitor `W_seq` max values across training. If max(W) consistently exceeds 1e6, the behavior policy is too stale and rollouts should be refreshed more frequently.

**Avoid:** Dividing `log_w_seq` by sequence length, square root of length, or any length-dependent factor. Length normalization introduces bias toward longer outputs and was the primary cause of collapse in ablation experiments.

**Avoid:** Using hard clipping (e.g., `clamp(W, 1-eps, 1+eps)`) alongside VESPO. The gamma kernel provides smooth, principled suppression -- adding clipping destroys the variational optimality guarantee and creates discontinuous gradients.

## Error Handling

- **NaN in phi computation:** If `log_w_seq` is extremely large (> 80), `exp(log_w_seq)` overflows. Clamp `log_w_seq` to a safe range (e.g., [-50, 50]) before computing `w_seq = exp(log_w_seq)`. This is a numerical guard, not the principled clipping VESPO avoids.
- **All-zero advantages:** If a prompt group produces identical rewards, advantages are zero and gradients vanish. Fall back to a uniform baseline or skip the batch.
- **Gradient norm spikes:** Occasional spikes are expected when the kernel encounters high-staleness batches. Use gradient clipping (max_norm=1.0) as a safety net, but persistent spikes indicate the staleness ratio should be reduced.
- **Phi values near zero for entire batch:** This means the kernel is suppressing nearly all trajectories. Check that `old_log_probs` corresponds to the correct behavior policy checkpoint and hasn't been overwritten.

## Limitations

- VESPO is designed for sequence-level RL objectives (e.g., outcome-based rewards on complete responses). It is not directly applicable to token-level reward models or dense reward signals without adaptation.
- The default hyperparameters were validated on mathematical reasoning tasks. Other domains (creative writing, code generation, instruction following) may benefit from tuning c1/c2 values.
- VESPO requires access to both current and behavior policy log-probabilities. Training setups that discard old log-probs (e.g., some online RLHF pipelines) must be modified to store them.
- The method was tested on models up to 30B parameters. Scaling behavior beyond this is plausible but unvalidated.
- VESPO addresses policy staleness but does not solve reward model quality, reward hacking, or data quality issues -- those remain orthogonal concerns.
