# MATA: Trainable Hierarchical Automaton for Multi-Agent Visual Reasoning

This skill enables Claude to design and implement multi-agent systems modeled as hierarchical finite-state automata (FSA) for visual reasoning tasks. Based on the MATA framework (ICLR 2026), the core idea is: a **hyper agent** (an LLM-based controller) selects which **specialized agent** to activate next, each agent runs a deterministic **sub-automaton** for reliable execution, and all agents communicate through **append-only shared memory**. This architecture produces interpretable, auditable reasoning chains while achieving state-of-the-art accuracy on VQA and visual grounding benchmarks.

## When to Use

- When building a multi-agent system that must route tasks to specialized agents based on query complexity (e.g., simple perception vs. multi-step reasoning)
- When implementing visual question answering pipelines that need transparent, step-by-step execution traces
- When designing an orchestration layer where an LLM decides which tool/agent to invoke next based on accumulated context
- When the user wants compositional visual reasoning that avoids the hallucination problems of monolithic vision-language models
- When building systems that need both collaboration (complementary agents) and competition (overlapping agents with selection)
- When implementing a finite-state machine where transitions are learned rather than hard-coded

## Key Technique

MATA models multi-agent orchestration as a **Mealy machine** `M = (S, S0, Sigma, Lambda, delta, Gamma)` with six states: three **agent states** (Specialized, Oneshot, Stepwise) and three **lifecycle states** (Initial, Final, Failure). The transition function `delta` is an LLM fine-tuned to map the current shared memory snapshot to the optimal next state. Unlike hand-crafted pipelines, the hyper agent *learns* when to use fast single-pass reasoning vs. iterative multi-step decomposition by training on 90K trajectory examples.

Each agent state encapsulates a **rule-based sub-automaton** -- a small deterministic FSA that handles micro-control. For example, the Oneshot agent runs: Code Generator -> Code Verifier -> Code Interpreter -> Return. The Stepwise agent loops: Instruction Generator -> Verification -> Code Generation -> Execution -> (loop or return). This two-level hierarchy gives you the best of both worlds: learned high-level strategy with deterministic low-level reliability.

The training data (MATA-SFT-90K) is generated by building **transition-trajectory trees**: for each image-query pair, the system branches over all possible next-state choices, scores leaf nodes with task metrics (accuracy, IoU), propagates scores bottom-up via max, and extracts (memory-snapshot, optimal-next-state) pairs. This transforms the agent routing problem into a standard supervised classification task over states.

## Step-by-Step Workflow

1. **Define the state space.** Enumerate your agent states (task executors) and lifecycle states (Initial, Final, Failure). Each agent state should correspond to a distinct reasoning capability. At minimum, implement three tiers: a fast perception agent, a single-pass compositional agent, and an iterative multi-step agent.

2. **Design shared memory as an append-only store.** Create a memory structure `M` that accumulates: the original query, intermediate variables, perception results, code execution history, verifier feedback, and state transition history. Use `M(t+1) = M(t) + delta_M(t)` -- never mutate, only append. This gives you a full audit trail.

3. **Implement each agent as a deterministic sub-automaton.** For each agent state, define a small FSA with fixed transitions between internal stages (e.g., generate -> verify -> execute -> return). Include error-correction loops: if verification fails, retry with modified parameters up to a fixed limit, then transition to the Failure lifecycle state.

4. **Build the hyper agent prompt template.** Construct a structured prompt for the transition function that includes: (a) the original task/query, (b) current shared memory contents, (c) state transition history so far, (d) available next states with brief capability descriptions, and (e) current step count. The LLM outputs the next state name wrapped in a parseable tag.

5. **Implement the transition loop.** Start at `Initial`. At each step: serialize shared memory into the hyper agent prompt, call the LLM to select the next state, execute that agent's sub-automaton, append results to shared memory, and check for termination (Final or Failure state, or step limit exceeded).

6. **Generate training trajectories (optional but recommended).** For a training set of (input, ground-truth) pairs, expand a trajectory tree by branching at each decision point over all possible next states. Score leaves with your task metric. Propagate scores bottom-up using max. Extract (memory-snapshot, best-next-state) pairs as supervised training data.

7. **Fine-tune the hyper agent.** Use the extracted (prompt, next-state) pairs to SFT the LLM that serves as your transition function. Use standard settings: AdamW optimizer, cosine learning rate decay with 5% warmup, batch size 64, ~8 epochs. This teaches the LLM to understand agent capabilities and route efficiently.

8. **Implement the output function.** When the automaton reaches the `Final` state, extract the answer from shared memory. Apply any final formatting or post-processing. If the automaton reaches `Failure`, return a structured error with the full memory trace for debugging.

9. **Add termination safeguards.** Set a maximum step count (e.g., 10-15 transitions). If the hyper agent oscillates between states or exceeds the limit, force transition to Failure. Log the full state history for diagnosis.

10. **Validate with interpretability checks.** After each run, verify that the shared memory trace forms a coherent reasoning chain. Each memory entry should clearly show what agent produced it, what input it consumed, and what output it generated.

## Concrete Examples

**Example 1: Visual Question Answering Pipeline**

User: "Build a multi-agent system that answers complex visual questions about images, routing between fast perception and multi-step reasoning."

Approach:
1. Define states: `{Initial, Specialized, Oneshot, Stepwise, Final, Failure}`
2. Implement shared memory as a Python dict with append-only lists
3. Build three agent sub-automatons

```python
from enum import Enum
from dataclasses import dataclass, field
from typing import Any

class State(Enum):
    INITIAL = "initial"
    SPECIALIZED = "specialized"  # Fast perception (object detection, simple QA)
    ONESHOT = "oneshot"          # Single-pass code generation + execution
    STEPWISE = "stepwise"        # Multi-step decomposition with verification loops
    FINAL = "final"
    FAILURE = "failure"

@dataclass
class SharedMemory:
    query: str = ""
    image_path: str = ""
    entries: list[dict[str, Any]] = field(default_factory=list)
    state_history: list[str] = field(default_factory=list)
    answer: Any = None

    def append(self, agent: str, content: dict):
        self.entries.append({"agent": agent, "step": len(self.entries), **content})

    def serialize(self) -> str:
        """Serialize memory into hyper agent prompt context."""
        lines = [f"Query: {self.query}", f"Steps taken: {len(self.entries)}",
                 f"State history: {' -> '.join(self.state_history)}"]
        for entry in self.entries[-5:]:  # Last 5 entries for context window
            lines.append(f"[{entry['agent']}] {entry.get('summary', '')}")
        return "\n".join(lines)


class HyperAgent:
    """LLM-based transition function: maps memory snapshot to next state."""

    PROMPT_TEMPLATE = """You are a routing controller for a visual reasoning system.
Given the current memory state, select the optimal next agent.

Available agents:
- specialized: Fast perception. Use for direct object detection, counting, simple attribute queries.
- oneshot: Single-pass reasoning. Use for moderately complex queries needing one code generation pass.
- stepwise: Multi-step reasoning. Use for complex compositional queries requiring decomposition.
- final: Task is complete. Use when the answer is available in memory.

Current memory:
{memory}

Output the next state as: <next_state>STATE_NAME</next_state>"""

    def __init__(self, llm_client):
        self.llm = llm_client

    def select_next_state(self, memory: SharedMemory) -> State:
        prompt = self.PROMPT_TEMPLATE.format(memory=memory.serialize())
        response = self.llm.generate(prompt)
        # Parse state from XML tags
        import re
        match = re.search(r"<next_state>(\w+)</next_state>", response)
        if match:
            return State(match.group(1).lower())
        return State.FAILURE


class MATAExecutor:
    """Main execution loop implementing the hierarchical automaton."""

    def __init__(self, hyper_agent, agents: dict, max_steps: int = 12):
        self.hyper = hyper_agent
        self.agents = agents  # Maps State -> callable sub-automaton
        self.max_steps = max_steps

    def run(self, query: str, image_path: str) -> dict:
        memory = SharedMemory(query=query, image_path=image_path)
        state = State.INITIAL
        memory.state_history.append(state.value)

        for step in range(self.max_steps):
            next_state = self.hyper.select_next_state(memory)
            memory.state_history.append(next_state.value)

            if next_state == State.FINAL:
                return {"answer": memory.answer, "trace": memory.entries}
            if next_state == State.FAILURE:
                return {"error": "Reasoning failed", "trace": memory.entries}

            # Execute the selected agent's sub-automaton
            agent = self.agents[next_state]
            agent.execute(memory)
            state = next_state

        return {"error": "Max steps exceeded", "trace": memory.entries}
```

Output: A system where the hyper agent routes "What color is the car?" to `Specialized` (one-shot perception) but routes "Is the number of red objects greater than the number of blue cylinders?" to `Stepwise` (multi-step decomposition).

**Example 2: Implementing a Sub-Automaton with Error Recovery**

User: "Implement the Oneshot agent as a deterministic sub-automaton with verification and retry."

```python
class OneshotAgent:
    """Sub-automaton: CodeGen -> Verify -> Execute -> Return.
    Deterministic transitions with error-correction loop."""

    def __init__(self, code_llm, verifier, interpreter, max_retries: int = 2):
        self.code_llm = code_llm
        self.verifier = verifier
        self.interpreter = interpreter
        self.max_retries = max_retries

    def execute(self, memory: SharedMemory):
        for attempt in range(self.max_retries + 1):
            # Stage 1: Generate code from query + memory context
            code = self.code_llm.generate(
                query=memory.query,
                context=memory.serialize(),
                image=memory.image_path
            )

            # Stage 2: Verify code (syntax, safety, API usage)
            is_valid, feedback = self.verifier.check(code)
            if not is_valid:
                memory.append("oneshot", {
                    "summary": f"Verification failed (attempt {attempt+1})",
                    "feedback": feedback
                })
                continue  # Retry with accumulated feedback in memory

            # Stage 3: Execute in sandbox
            result, exec_error = self.interpreter.run(code)
            if exec_error:
                memory.append("oneshot", {
                    "summary": f"Execution error (attempt {attempt+1})",
                    "error": str(exec_error)
                })
                continue  # Retry

            # Stage 4: Return result to shared memory
            memory.append("oneshot", {
                "summary": f"Success: {str(result)[:100]}",
                "code": code, "result": result
            })
            memory.answer = result
            return

        # All retries exhausted -- signal failure to hyper agent
        memory.append("oneshot", {"summary": "All retries exhausted"})
```

**Example 3: Building Transition-Trajectory Training Data**

User: "Generate training data for the hyper agent by building trajectory trees."

```python
def build_trajectory_tree(image, query, ground_truth, agents, metric_fn):
    """Expand all possible state transitions, score leaves, extract training pairs."""
    agent_states = [State.SPECIALIZED, State.ONESHOT, State.STEPWISE]

    def expand(memory: SharedMemory, depth: int, max_depth: int = 4):
        if depth >= max_depth:
            score = metric_fn(memory.answer, ground_truth)
            return {"score": score, "children": {}, "memory_snapshot": memory.serialize()}

        best_score = 0.0
        best_state = None
        children = {}

        for state in agent_states:
            branch_memory = deepcopy(memory)
            agents[state].execute(branch_memory)
            child = expand(branch_memory, depth + 1, max_depth)
            children[state.value] = child

            if child["score"] > best_score:
                best_score = child["score"]
                best_state = state

        return {
            "score": best_score,
            "best_next": best_state.value if best_state else None,
            "children": children,
            "memory_snapshot": memory.serialize()
        }

    root_memory = SharedMemory(query=query, image_path=image)
    tree = expand(root_memory, depth=0)

    # Extract (memory_snapshot, optimal_next_state) training pairs
    training_pairs = []
    def extract_pairs(node):
        if node["best_next"]:
            training_pairs.append({
                "prompt": node["memory_snapshot"],
                "label": node["best_next"]
            })
        for child in node["children"].values():
            extract_pairs(child)

    extract_pairs(tree)
    return training_pairs
```

Output: A list of (memory-snapshot, optimal-next-state) pairs ready for supervised fine-tuning, where each label is the state choice that leads to the highest downstream task metric.

## Best Practices

- **Do:** Keep shared memory append-only. Never mutate previous entries. This guarantees a complete audit trail and makes debugging straightforward. The union operation `M(t+1) = M(t) + delta` is fundamental to MATA's interpretability.

- **Do:** Make sub-automatons fully deterministic with fixed transition graphs. The hyper agent handles strategic uncertainty; sub-agents should handle tactical execution reliably. This separation of concerns is what makes the system robust.

- **Do:** Include the full state transition history in the hyper agent's prompt. The controller needs to know what has already been tried to avoid oscillation and infinite loops.

- **Do:** Serialize only the most recent memory entries (e.g., last 5) plus summary statistics when building hyper agent prompts. Full memory dumps can exceed context limits on long reasoning chains.

- **Avoid:** Letting the hyper agent make fine-grained tool calls directly. It should only select *which agent* to activate. The agent's internal sub-automaton handles tool selection and execution order.

- **Avoid:** Skipping the verification stage in sub-automatons. The generate-verify-execute pattern with retry loops is critical for catching errors before they propagate to shared memory and corrupt downstream reasoning.

## Error Handling

- **Hyper agent returns unparseable output:** Default to the `Failure` state. Log the raw LLM output for debugging. Consider re-prompting once with a more constrained format instruction.
- **Sub-automaton exhausts retries:** The agent writes a failure summary to shared memory and returns control to the hyper agent. The hyper agent can then route to a different agent (e.g., escalating from Oneshot to Stepwise) or transition to Failure.
- **Step limit exceeded:** Force transition to Failure. Inspect the state history for oscillation patterns (e.g., Specialized -> Oneshot -> Specialized -> Oneshot). If detected, add anti-oscillation logic that prevents revisiting the same state consecutively.
- **Shared memory grows too large:** Implement a summarization step that condenses older entries while preserving key variables and results. Only the summary and recent entries go into the hyper agent prompt.
- **Code execution errors in sandboxed agents:** Capture the full traceback, append it to shared memory as feedback, and let the sub-automaton retry with the error context. After max retries, propagate to the hyper agent.

## Limitations

- **Vision model dependency:** MATA orchestrates agents but each agent still relies on underlying vision-language models for perception. The framework cannot compensate for fundamental failures in the base models' perceptual ability.
- **Training data cost:** Building trajectory trees requires running all possible agent paths for each training example, which scales as O(|agents|^depth). This is computationally expensive for large training sets.
- **Fixed agent roster:** The state space is defined at design time. Adding a new agent type requires updating the automaton definition, regenerating training data, and re-fine-tuning the hyper agent.
- **Single-image reasoning:** MATA was designed and evaluated on single-image visual reasoning. Multi-image or video reasoning would require extending the shared memory schema and potentially adding new agent types.
- **Hyper agent context limits:** For very long reasoning chains (>10 steps), the serialized memory may exceed the LLM's effective context window, degrading transition quality.
