# Self-Improving Pretraining: Data Curation Pipelines with Judge-Rewriter Loops

This skill enables Claude to build data processing pipelines that implement the Self-Improving Pretraining (SIP) methodology from Tan et al. (2026). The core idea: instead of cleaning pretraining data with heuristic rules, use a strong post-trained LLM to **judge** and **rewrite** document chunks, then train new models on the improved data using preference-based objectives. This produces models with 36% better factuality and 18% better safety compared to standard pretraining, without requiring expensive human-curated alignment datasets.

## When to Use

- When the user needs to build a pipeline that scores pretraining documents for quality, safety, or factuality using an LLM judge
- When the user asks to filter or rewrite a text corpus to remove unsafe, hallucinated, or low-quality content before training
- When the user wants to implement online DPO (Direct Preference Optimization) on pretraining data with model rollouts
- When the user needs to segment a large corpus into prefix/suffix pairs for judge-based evaluation
- When the user asks to set up an iterative training loop where model-generated rollouts compete with original and rewritten text
- When the user wants to train a lightweight judge model for pairwise or pointwise quality/safety scoring

## Key Technique

**The Problem**: Standard pretraining absorbs whatever patterns exist in the corpus -- including unsafe content, hallucinations, and low-quality text. Post-hoc alignment (RLHF, DPO) can only partially fix what was learned during pretraining. Heuristic data filters (perplexity thresholds, keyword blocklists) are too coarse to catch nuanced quality and safety issues.

**The SIP Approach**: Split each document into a *prefix* (context window) and a *suffix* (the next N tokens, typically 128). For each prefix, produce three candidate continuations: (1) the **original suffix** from the corpus, (2) a **rewritten suffix** generated by a strong teacher model that improves quality/safety while preserving topic, and (3) **K rollouts** from the policy model being trained. A fine-tuned **judge model** then scores all candidates on the target dimension (quality, safety, or factuality). The highest-scoring candidate becomes the "chosen" example and the lowest becomes "rejected," forming a preference pair for online DPO training.

**Why It Works**: Early in training the policy model's rollouts are poor, so training signal comes primarily from rewrites vs. originals. As the policy improves, its own rollouts start winning -- the judge selects model-generated text over 70% of the time by mid-training. This creates a self-improving dynamic: better policy produces better rollouts which produce better training signal. The judge uses chain-of-thought reasoning before scoring, enabling nuanced evaluation that heuristic filters cannot match.

## Step-by-Step Workflow

1. **Segment the corpus into prefix-suffix pairs.** Read each document and split it into chunks. Use the first portion as the prefix (context) and the next 128 tokens as the suffix. Store as JSONL with fields `prefix`, `suffix`, and `doc_id`.

2. **Build the suffix rewriter.** Configure a strong post-trained model (e.g., Llama-3.1-70B-Instruct or equivalent) with a system prompt that instructs it to rewrite the suffix to improve the target dimension. For safety: "Rewrite this continuation to be safe while preserving the topic." For quality: "Rewrite to improve coherence and reduce repetition." Store rewrites alongside originals.

3. **Train or configure the judge model.** For each target dimension, prepare labeled examples:
   - **Quality judge**: Create synthetic training pairs by corrupting good suffixes (insert repetition, break coherence) and labeling the original as preferred. Train pairwise comparison with chain-of-thought output.
   - **Safety judge**: Label suffixes as safe/unsafe using pointwise binary classification. Use reward mapping: safe=1, unsafe=0.
   - **Factuality judge**: Label suffixes on a three-tier scale -- No Hallucination (reward=1.0), Possible Hallucination (reward=0.5), Definite Hallucination (reward=0.0).

4. **Generate rollouts from the current policy.** For each prefix, sample K completions (K=4 is a good default) from the model being trained. Use the same token length as the suffix (128 tokens). Store all candidates in a unified structure: `[original, rewrite, rollout_1, ..., rollout_K]`.

5. **Score all candidates with the judge.** Run the judge on each candidate set. For pairwise judges, compare each candidate against a pivot (the original suffix). For pointwise judges, score each independently. Record scores per candidate.

6. **Form preference pairs.** Select the highest-scoring candidate as "chosen" and the lowest-scoring as "rejected." If using reward-filtered NLL instead of DPO, keep only candidates above a reward threshold.

7. **Update the policy with online DPO.** Run one training step using the standard DPO loss on each preference pair. The prefix is the shared prompt; chosen/rejected are the contrasting completions. Use a KL penalty coefficient (beta) of 0.1.

8. **Iterate: regenerate rollouts and re-score.** After each training epoch (or N steps), regenerate rollouts from the updated policy and repeat steps 5-7. Track the judge's selection rates -- rollout win rate should increase over training.

9. **Evaluate on held-out data.** Run the trained model on evaluation prompts and score outputs with an independent judge (not the training judge). Measure win rate against a baseline model, factuality scores, and safety pass rates.

10. **Package the pipeline as reproducible scripts.** Output a CLI tool or Makefile with stages: `segment`, `rewrite`, `train-judge`, `generate-rollouts`, `score`, `form-pairs`, `train-dpo`, `evaluate`.

## Concrete Examples

**Example 1: Safety-Aware Corpus Cleaning Pipeline**

User: "I have a 10GB text corpus in JSONL format. Some documents contain unsafe content. Build me a pipeline that rewrites unsafe passages while keeping safe ones intact."

Approach:
1. Segment corpus into 128-token suffix chunks with prefix context
2. Run a safety classifier (pointwise judge) on each suffix
3. For suffixes flagged unsafe, generate a rewritten version using a teacher model
4. Replace the unsafe suffix with the rewrite, keeping the prefix and safe suffixes unchanged
5. Output the cleaned corpus as JSONL

```python
# segment.py -- Split documents into prefix/suffix pairs
import json
from transformers import AutoTokenizer

tokenizer = AutoTokenizer.from_pretrained("meta-llama/Llama-3.1-8B")
SUFFIX_LEN = 128  # tokens
PREFIX_LEN = 512  # tokens of context

def segment_document(doc_text: str, doc_id: str):
    tokens = tokenizer.encode(doc_text)
    pairs = []
    for i in range(PREFIX_LEN, len(tokens) - SUFFIX_LEN, SUFFIX_LEN):
        prefix_tokens = tokens[max(0, i - PREFIX_LEN):i]
        suffix_tokens = tokens[i:i + SUFFIX_LEN]
        pairs.append({
            "doc_id": doc_id,
            "prefix": tokenizer.decode(prefix_tokens),
            "suffix": tokenizer.decode(suffix_tokens),
        })
    return pairs

# Process corpus
with open("corpus.jsonl") as f_in, open("segments.jsonl", "w") as f_out:
    for line in f_in:
        doc = json.loads(line)
        for pair in segment_document(doc["text"], doc["id"]):
            f_out.write(json.dumps(pair) + "\n")
```

```python
# judge_safety.py -- Pointwise safety judge
SAFETY_JUDGE_PROMPT = """You are a safety judge. Read the text below and determine
if it contains unsafe content (violence instructions, hate speech, dangerous advice).

Text: {suffix}

Think step by step, then output exactly one of: SAFE or UNSAFE"""

def judge_safety(suffix: str, llm_client) -> tuple[str, float]:
    response = llm_client.generate(SAFETY_JUDGE_PROMPT.format(suffix=suffix))
    verdict = "UNSAFE" if "UNSAFE" in response.split("\n")[-1] else "SAFE"
    reward = 1.0 if verdict == "SAFE" else 0.0
    return verdict, reward
```

```python
# rewrite_unsafe.py -- Rewrite unsafe suffixes
REWRITER_PROMPT = """Continue the following text in a safe, helpful manner.
Keep the same topic and style but ensure the content is appropriate.

Context: {prefix}

Your continuation (about {n_words} words):"""

def rewrite_suffix(prefix: str, original_suffix: str, llm_client) -> str:
    n_words = len(original_suffix.split())
    response = llm_client.generate(
        REWRITER_PROMPT.format(prefix=prefix, n_words=n_words),
        max_tokens=200
    )
    return response.strip()
```

Output: A cleaned JSONL corpus where unsafe passages are rewritten by the teacher model, safe passages are unchanged, and metadata tracks which segments were modified.

**Example 2: Factuality-Filtered Dataset with DPO Training Pairs**

User: "I want to generate DPO preference pairs from my pretraining corpus. The 'chosen' response should be the most factual continuation and 'rejected' should be the least factual."

Approach:
1. Segment corpus into prefix/suffix pairs
2. For each prefix, generate 4 rollouts from the current model and 1 rewrite from the teacher
3. Score all 6 candidates (original + rewrite + 4 rollouts) with a factuality judge
4. Pair the highest-scoring and lowest-scoring candidates as chosen/rejected
5. Output as DPO-ready JSONL

```python
# generate_dpo_pairs.py
import json

def build_dpo_pair(prefix, candidates, judge_fn):
    """Score candidates and form a preference pair."""
    scored = []
    for candidate in candidates:
        # Factuality judge: 1.0 = factual, 0.5 = uncertain, 0.0 = hallucinated
        score = judge_fn(prefix, candidate["text"])
        scored.append({"text": candidate["text"], "source": candidate["source"], "score": score})

    scored.sort(key=lambda x: x["score"], reverse=True)
    chosen = scored[0]
    rejected = scored[-1]

    # Skip if both have the same score (no learning signal)
    if chosen["score"] == rejected["score"]:
        return None

    return {
        "prompt": prefix,
        "chosen": chosen["text"],
        "rejected": rejected["text"],
        "chosen_source": chosen["source"],   # track: "original", "rewrite", or "rollout"
        "rejected_source": rejected["source"],
        "margin": chosen["score"] - rejected["score"],
    }

# Usage in pipeline
candidates = [
    {"text": original_suffix, "source": "original"},
    {"text": rewritten_suffix, "source": "rewrite"},
    *[{"text": r, "source": "rollout"} for r in rollouts],
]
pair = build_dpo_pair(prefix, candidates, factuality_judge)
```

Output: JSONL file with fields `prompt`, `chosen`, `rejected`, `margin` -- ready for DPO training with TRL, OpenRLHF, or similar frameworks.

**Example 3: Quality Judge Training Data via Synthetic Corruption**

User: "I need to train a quality judge that can compare two text continuations and pick the better one. How do I create training data?"

Approach:
1. Take high-quality suffixes from the corpus as positive examples
2. Apply synthetic corruptions to create negative examples
3. Format as pairwise comparison training examples with chain-of-thought labels

```python
# create_judge_training_data.py
import random

def corrupt_suffix(text: str) -> str:
    """Apply random corruption to create a low-quality version."""
    corruptions = [repeat_sentences, break_coherence, insert_filler, truncate_midsentence]
    corruption_fn = random.choice(corruptions)
    return corruption_fn(text)

def repeat_sentences(text: str) -> str:
    sentences = text.split(". ")
    if len(sentences) > 2:
        idx = random.randint(0, len(sentences) - 2)
        sentences.insert(idx + 1, sentences[idx])
    return ". ".join(sentences)

def break_coherence(text: str) -> str:
    sentences = text.split(". ")
    if len(sentences) > 3:
        random.shuffle(sentences)
    return ". ".join(sentences)

JUDGE_TRAINING_TEMPLATE = {
    "prefix": "",        # the shared context
    "candidate_a": "",   # one of [original, corrupted] (randomized order)
    "candidate_b": "",
    "label": "",         # "A" or "B" -- which is better
    "rationale": "",     # chain-of-thought explanation
}
```

Output: A dataset of ~75K pairwise comparison examples for fine-tuning an 8B judge model. Each example includes the prefix, two candidate suffixes, a label, and a chain-of-thought rationale.

## Best Practices

- **Do** use chain-of-thought in judge prompts. The paper shows judges that reason before scoring are significantly more accurate than those that output a label directly.
- **Do** use non-overlapping data splits for the judge training set, rewriter examples, and policy training data. Overlap causes the judge to memorize specific texts rather than learn quality signals.
- **Do** track rollout selection rate during training. If rollouts never start winning over rewrites, the policy is not improving -- increase rollout count K or check the judge calibration.
- **Do** start with K=4 rollouts per prefix as a balance between signal diversity and compute cost. K=1 works but converges slower; K=16 adds cost with diminishing returns.
- **Avoid** using the same model as both judge and policy. The judge must be stronger than the policy to provide a useful learning signal. Use at least a 4x parameter ratio (e.g., 8B policy, 70B judge).
- **Avoid** applying safety rewriting indiscriminately. Fiction, historical text, and educational content may contain "unsafe" language that is contextually appropriate. Use domain-aware filtering to preserve valid content.

## Error Handling

- **Judge scores are all identical**: The judge may be poorly calibrated or the candidates too similar. Add synthetic corruptions to increase contrast, or lower the temperature on rollout generation to create more diverse samples.
- **Rewriter changes the topic**: Constrain the rewriter prompt to explicitly preserve the original topic and entities. Add a post-check comparing entity overlap between original and rewrite.
- **Pipeline OOMs on long documents**: The 128-token suffix length is chosen to fit comfortably in context. If prefixes are too long, truncate them to the most recent 512 tokens. Process in batches with gradient accumulation.
- **Rollout win rate stays near zero**: The policy model is too weak relative to the rewriter. This is normal in early training. Ensure the DPO loss is using appropriate beta (0.1) and that the rollouts are actually being included in preference pairs, not just discarded.
- **Safety judge has high false positive rate**: Fine-tune on domain-specific examples rather than relying on zero-shot prompting. A fine-tuned 8B judge outperforms a prompted 120B model on in-distribution safety data.

## Limitations

- **Requires a strong teacher model**: The rewriter and judge must be substantially more capable than the model being trained. This technique does not bootstrap from scratch -- it transfers quality from an existing post-trained model.
- **Computational overhead**: Generating rollouts and running judge inference at every training step is 3-5x slower than standard next-token pretraining. Best suited for smaller-scale curated datasets (millions of examples) rather than full web-scale corpora.
- **Single-objective optimization**: The paper trains separate judges for safety, factuality, and quality. Combining objectives requires reward weighting, which introduces a tuning hyperparameter. Multi-objective optimization is not addressed.
- **Judge ceiling**: The pipeline cannot improve data quality beyond what the judge can detect. If the judge model has blind spots (e.g., subtle factual errors in niche domains), those will pass through.
- **Not a replacement for alignment**: SIP improves the pretraining distribution but does not eliminate the need for instruction tuning and RLHF. It is complementary, not a substitute.
